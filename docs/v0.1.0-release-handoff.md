# Fresh-session prompt: publish Throughline v0.1.0 and run the first user journey

Copy the prompt below into a fresh coding session.

---

Work in the current Throughline repository. The checkout directory may still be named `workgraph`;
do not infer the product name from that local path.

Task: make Throughline publicly accessible and ship the smallest release-engineering milestone
required for a first user to discover, download, verify, install, configure, and run Throughline
`v0.1.0`. Prove it with the bounded first user journey. Do not add domain features.

Definition of done:

> A target user without a source checkout or Go toolchain can find the public repository, download
> the correct archive, verify its checksum, install `throughline` on `PATH`, configure one supported
> MCP client, initialize a local workspace, and complete the researcher/reviewer journey using the
> installed binary.

Read completely before deciding:

- `AGENTS.md`
- `README.md`
- `docs/product/0001-market-testable-v0.1.md`
- `docs/implementation-handoff.md`
- `docs/development.md`
- all `docs/adr/*.md`, especially ADR 0014
- this handoff

Use Graphify to inspect the current architecture. Inspect `git status` first and preserve all
existing changes; do not reset, discard, or overwrite unrelated work.

Current product decisions:

- Product: `Throughline`; executable/module/repository slug: `throughline`.
- Go module: `github.com/dennisschroeder/throughline`.
- Workspace: `.throughline/config.toml` and `.throughline/throughline.db`.
- `v0.1.0` is the market-testable headless release defined in Product Decision 0001.
- SQLite remains authoritative; MCP, CLI, and future UI share the application layer.
- Throughline records external actions and evidence but never executes external effects.
- Do not build auth, policy language, web UI, orchestration, multi-workspace/network transport,
  semantic search, broad CLI parity, or distributed coordination.

Repository/release prerequisites to verify:

- No Git remote was configured when this handoff was written. Confirm the public repository will be
  `github.com/dennisschroeder/throughline`; changing or publishing a remote repository is an external
  action and requires explicit user confirmation.
- The local checkout directory may be renamed separately; it is not a product correctness blocker.
- Do not create or push the `v0.1.0` tag or publish a GitHub Release without explicit confirmation.
- Confirm the public name, repository slug, module path, release artifact names, MCP server name,
  workspace path, and documentation all consistently use Throughline/`throughline`.

Implement the minimum coherent release path:

1. Prepare the public repository as the product front door: concise positioning, scope boundary,
   supported platforms, trusted-local security caveat, license, installation path, and one obvious
   quickstart. Do not add marketing claims that the bounded scenario has not proven.
2. Add deterministic version reporting (`throughline version` or `--version`) with release-time
   version, commit, and build date injection plus useful development defaults and tests.
3. Add CI for formatting, vet, full tests, normal build, and `CGO_ENABLED=0` build.
4. Add a reproducible release configuration triggered by `v*` tags. Prefer a small GoReleaser setup
   unless repository constraints make a simpler native workflow safer.
5. Produce archives at minimum for macOS arm64 and Linux amd64; macOS amd64 and Linux arm64 are
   desirable when they add little complexity. Include the binary, README, LICENSE, and checksums.
6. Add tested download/install, checksum verification, upgrade, backup/restore, uninstall, and MCP
   client configuration instructions. Use commands that consume release artifacts rather than the
   Go toolchain. A package manager, website, and hosted service are not required for `v0.1.0`.
7. Add a release checklist covering repository creation/remote setup, public visibility, clean CI,
   tag, artifact dry run, checksum verification, fresh-machine smoke, release notes, publish, and
   post-publish install test.
8. Run the bounded no-Git two-client MCP workflow with the packaged binary. Retain
   execution-neutral external-action semantics and record the commands/results in a concise first
   user journey document.

First user journey to prove from an installed artifact:

1. Download the platform archive from the public `v0.1.0` release and verify its checksum.
2. Install `throughline` on `PATH`; confirm `throughline version` reports `v0.1.0`.
3. In an empty non-Git directory, run `throughline init` and verify
   `.throughline/throughline.db` exists.
4. Configure two independent MCP-capable client sessions against `throughline mcp <workspace>`.
5. Create a domain-neutral research objective, record context, propose a plan containing a dossier
   and downstream work requiring that accepted dossier, and approve the plan.
6. Transition to execution, make the dossier ready, claim it from the researcher session, and prove
   the reviewer session receives a deterministic claim conflict.
7. Record progress, create the dossier OutputRevision, validate it from the reviewer session, and
   prove the downstream item becomes ready through output reuse.
8. Restart a client and resume through objective context and changes without copying a transcript.
9. Propose one harmless scoped ExternalAction, bind approval to the exact principal and subject,
   record externally observed result/evidence, and confirm Throughline itself performs no effect.

Acceptance criteria:

- `rg -i 'workgraph'` finds only ADR 0014's rename history and this handoff's local checkout-path
  warning.
- `go mod` and all imports use `github.com/dennisschroeder/throughline`.
- `go run ./cmd/throughline version` reports a useful development version.
- A local release dry run produces correctly named archives and a checksum file without publishing.
- Extracted artifacts run on their target platform, report `v0.1.0` when built from the release tag,
  initialize `.throughline/throughline.db`, and start MCP stdio.
- A clean environment with no repository and no Go toolchain completes installation and the first
  user journey from the packaged binary.
- The public repository and release page contain enough information to choose an artifact, install
  it, configure MCP, understand the trusted-local boundary, and report a problem.
- `gofmt`, `go vet ./...`, `go test ./...`, `go build ./...`, and
  `CGO_ENABLED=0 go build ./...` all pass.
- The Product Decision 0001 functional and operational `v0.1.0` criteria are either verified or
  explicitly reported as remaining external/manual gates.

Use the local development loop until clean. Keep changes minimal. Report files changed, commands and
results, dry-run artifact names, first-journey evidence, remaining manual/external gates, and the
exact safe commands the maintainer should run to make the repository public and publish `v0.1.0`.
Do not stop at a plan.

## Outcome

Executed in full, including publishing. Public repository, tag, and release exist.

**Repository and release**: `github.com/dennisschroeder/throughline`, public.
[`v0.1.0`](https://github.com/dennisschroeder/throughline/releases/tag/v0.1.0) published with four
archives (`throughline_0.1.0_{darwin,linux}_{amd64,arm64}.tar.gz`) plus
`throughline_0.1.0_checksums.txt`. CI green on push to `main`; release workflow green on the `v0.1.0`
tag.

**Files changed** (commit `5b125a5`, 12 files, +750/-77): `internal/cli/version.go` (new),
`internal/cli/cli.go`, `internal/cli/cli_test.go`, `.github/workflows/ci.yml` (new),
`.github/workflows/release.yml` (new), `.goreleaser.yaml` (new), `.gitignore`, `README.md`,
`docs/development.md`, `docs/install.md` (new), `docs/release-checklist.md` (new),
`docs/graphs/v0-1-0-release-engineering.md` (new, execution trail).

**Verification**: `gofmt -l cmd internal`, `go vet ./...`, `go test ./...`, `go build ./...`,
`CGO_ENABLED=0 go build ./...`, and 20x `TestConcurrentAgentsCannotBothClaimWorkItem` all pass.
`rg -i 'workgraph'` matches only ADR 0014 and this document's local checkout-path warning, as
required by the acceptance criteria.

**Release dry run**: `goreleaser release --snapshot --clean` produced the four correctly-named
archives plus a checksums file; the extracted binary ran and reported the injected snapshot
version.

**First user journey**: fully proven from the real published artifact — see
[docs/first-user-journey.md](first-user-journey.md) for commands, results, and a
criterion-by-criterion mapping to Product Decision 0001's exit criteria. In summary: real download
and checksum verification, install on `PATH`, `throughline version` reporting `v0.1.0` from the
release commit, `throughline init` in a non-Git directory, a two-independent-MCP-client scenario
(deterministic claim conflict, output-reuse readiness, restart/resume through objective context and
change cursors, and a full external-action lifecycle — proposed, granted to the exact principal and
subject, executed with zero real network calls, recorded as succeeded).

**A real defect caught and fixed before publishing**: code review found the GoReleaser ldflags used
`{{.Version}}` (which strips the tag's leading `v`) to inject the CLI's reported version, which
would have shipped `throughline version` reporting `0.1.0` rather than the acceptance-criteria's
required `v0.1.0`. Fixed to `{{.Tag}}` and verified live against both a local snapshot build and the
real published release. A second finding — `release.yml` missing an explicit
`permissions: contents: write` block — was also fixed and confirmed load-bearing when the real
release workflow subsequently succeeded with it in place.

**Remaining manual/external gates**: none required for `v0.1.0` itself. Upgrade and uninstall flows
are documented in [docs/install.md](install.md) but not independently re-exercised end-to-end in
this pass (see [docs/first-user-journey.md](first-user-journey.md) for the full list). The V1.0
market-exit criteria (three independent users, real workflows, 15-minute median install time) are
explicitly out of scope for `v0.1.0` per Product Decision 0001.

Execution trail, including per-node budgets spent and design-vs-reality feedback, is in
[docs/graphs/v0-1-0-release-engineering.md](graphs/v0-1-0-release-engineering.md).
